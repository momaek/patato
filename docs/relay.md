# 中转线路设计

> 2026-11-20 · 状态：阶段 1–3 已实现（未做真机关口验收，见文末「实现说明」）。排期、阶段关口和落地访问统计见 [中转线路与落地访问监控计划](monitoring.md)，本文是其中「线路、入口与托管转发」的详细设计。两份文档冲突时以计划为准，并同步修改本文。

## 背景

一个落地节点在国内直连往往很慢或连不上，所以客户端先连国内或香港的中转机器，由中转原样转发到落地节点。转发可能不止一跳。现网链路和手写转发的问题见计划的「现状」一节。归纳起来：

- 新增一个落地，要逐台登录中转机器挑端口、写规则；删掉落地后，规则会一直留着。
- 某一跳挂了，面板只看到一批节点同时不通，看不出是哪台中转。
- 落地换了 IP，要逐跳改规则，或者靠额外的 DNS 刷新脚本。
- socat 每个连接 fork 一个进程，小内存中转机器上常驻几百个进程。
- 看不到每条线路走了多少流量。整段 DNAT 规则的计数只是首包，也分不出线路。

## 目标

1. **转发规则零维护**：运营者只说「这些节点走 广州 → 香港」，Patato 自动分配端口、下发规则；节点删除、换机器、换 IP 时，规则自动更新或清理。
2. **订阅里每个入口一条**，例如「洛杉矶 SS · 广州中转」，地址是第一跳。
3. **链路可观测**：每条线路的在线状态和上下行流量；任一跳故障时能说出是哪台机器、影响几条线路。
4. **默认内核转发**，没有条件时才退回用户态。

不做：

- 中转上按用户统计流量。中转只看到加密字节，按用户计费照旧由落地负责。
- 接管 Patato 以外的转发规则。机器上已有的 iptables 和 socat 不改不删。
- 负载均衡、多入口自动择优、按线路计费。

## 概念

数据模型（`routes`、`node_entries`、`forwards` 等表）见计划的「概念与数据模型」。

| 概念 | 含义 |
| --- | --- |
| 落地节点 | 现有的 Patato 节点：跑代理协议、认用户、计流量，不变 |
| 中转机器 | 已接入 patato-node、承担转发的 `machines`。一台机器可以既做落地又做中转 |
| 线路（route） | 有序的中转机器列表，例如「广州 → 香港」=［中转 A，中转 B］，可复用 |
| 入口（entry） | 节点的一个对外地址，订阅里的一条。直连入口没有线路，中转入口绑定一条线路 |
| 转发（forward） | 入口在某一跳上的一条规则：`本机端口 → 下一跳地址:端口`，TCP 和 UDP 都转 |

一个入口经过几跳，就生成几条转发。最后一跳的下一跳是落地机器的对外地址和节点的对外端口（`port`；NAT 落地由商家把对外端口映射到监听端口 `server_port`，非 NAT 落地两者相同）：

```
入口 = 节点 N（落地 L，对外端口 33455）经线路［A, B］
  转发 1：A:41010 → B 的对外地址:B 的外网端口
  转发 2：B:41010 → L 的对外地址:33455
  订阅：A 的对外地址:A 的外网端口
```

转发有三种 `mode`：

| mode | 谁执行 | 用途 |
| --- | --- | --- |
| `nft` | patato-node，内核转发 | 默认 |
| `userspace` | patato-node 内置的 sing-box | 没有 nftables、需要 IPv6 入口或运营者指定时 |
| `manual` | 运营者手写的规则 | 只登记端口和下一跳，Patato 不下发、不计流量。用于从 Xboard 导入的现有链路 |

此外，一个入口也可以不带线路、只填地址和端口，例如购买的 IPLC。这类入口的状态只跟随落地节点。

## 运营者怎么用

所有操作都先预演，再执行或转审批。命令名以计划的「契约与代码改动范围」为准。

```bash
# 一次性：设置中转机器的对外地址和可分配端口段（NAT 机器写明外网端口映射，见计划「机器的网络属性」）
patato machine set <中转 A> --public-address <给客户端的域名> --port-range 40000-49999
patato machine set <NAT 机器> --public-address <商家给的域名> --nat --port-range 20000-20099:30000

# 建线路
patato route create gz-hk --name 广州中转 --via <中转 A>,<中转 B>

# 让节点走这条线路：按套餐或节点选，一次挂一批
patato route apply gz-hk --plan <套餐> --dry-run
patato route apply gz-hk --plan <套餐>

# 单个节点的入口
patato node entry add <节点> --route gz-hk
patato node entry add <节点> --route hk --address entry.example.com --port 61001   # 第一跳前面还有一层自管转发（如入口机整段 DNAT）：订阅用这个地址和端口
patato node entry disable <节点> <入口>
patato node entry adopt <节点> <入口> --route gz-hk --forward gz-01:60001=hk:60001 --forward hk-01:60001=落地:443   # 链路发现确认后登记手写转发

# 查看
patato route list
patato route traffic --since 7d
```

Agent 收到「SS 节点都走广州到香港」时，就会执行上面这几条命令。预演结果列出每一跳要占用的端口、新增的订阅条目，以及受影响的用户数。

## 入口组

有的线路第一跳不是一台机器，而是几台机器共用一个域名：例如 `reality.ckneedu.com` 有时解析到洛杉矶的 A，有时解析到香港的 B。每台机器上都有一份相同的转发，同一个端口转到同一个落地，域名解析到哪台都能用。

**做法**：线路可以带一个入口组。

- **成员**：`entry_peers` 列出和第一跳一起承担入口的其他机器。成员不能同时是线路的一跳。
- **入口地址**：`entry_address` 是这组机器共用的域名，有成员时必须填写。订阅里，经过这条线路的入口都用这个地址；入口自己覆盖的地址优先。
- **端口**：每个入口在第一跳和每个成员上对外用同一个端口，订阅里只有一条入口。分配时先找所有跳和成员都空闲的同号端口，找不到再只要求第一跳和成员对齐。NAT 成员按外网端口对齐。
- **镜像转发**：第一跳之外，每个成员上还有一条转发（`forwards.mirror`），与第一跳的转发监听同一个对外端口、转到同一个下一跳。patato-node 不区分镜像和普通转发。

```bash
patato route create reality --name Reality --via bwh-la --entry-peers hnyun-hk --entry-address reality.ckneedu.com
patato route apply reality --plan <套餐>                       # 两台机器上各开同号端口
patato route update reality --entry-peers hnyun-hk,sg-01         # 加成员：给已有入口补镜像
patato route update reality --entry-peers ""                     # 取消入口组（敏感）
```

**域名切换**：Patato 不改 DNS。服务端每分钟解析一次入口地址，把结果和成员的 IP 比对（对外地址本身是 IP 时用它，否则用 tolato 上报的 IP），得出域名当前指向哪几台机器。`route show` 会标出「当前解析」。

**可用性**：其余跳与普通线路相同，第一跳按下面判断：

- 域名指向的每台成员都要可用。轮询解析到多台时，客户端可能连到其中任何一台。
- 还没解析过、连续解析失败超过 5 分钟，或指向的 IP 不属于任何成员时，任一成员可用即可，不因为不知道指向而撤下入口。
- 成员掉线时，告警会说明它在入口组里。只有域名正指向它时入口才撤下，把解析切到其他成员即可恢复。

**修改与风险**：

| 操作 | 等级 |
| --- | --- |
| 建带入口组的线路、给已有入口的线路加成员 | 常规。新成员必须已接入 patato-node，同号端口被占时拒绝，指出入口和端口 |
| 用同样的成员列表再提交一次 | 常规。补齐缺少的镜像、删掉不在组里的机器上的镜像；没有可补的时返回 `nothing_to_change` |
| 去掉成员 | 有入口时敏感。删除该成员上的镜像，域名还指向它的客户端会断开 |
| 修改已在使用的入口地址 | 敏感，订阅改变 |

限制：

- 改跳和改入口组要分两次提交。
- 修改入口组时，执行阶段按当时的全部入口重新对齐镜像，预演之后新加的入口也包括在内。
- 有入口组且线路上已有入口时，第一跳不能更换（`entry_group_first_hop`），要换就新建线路后迁移入口。
- 成员的端口映射改动如果会让对外端口和其他成员对不上，会被拒绝（`entry_group_port_mismatch`）。
- 手写（manual）入口不建镜像。
- 线路流量和入口流量都把第一跳和所有成员的读数加在一起。

## 端口分配

- **端口段**：每台机器有可分配端口段（`machines.port_ranges`，可多段），默认 `40000-49999`，可以按机器覆盖，例如改成云厂商安全组已放行的范围。只在段内分配。NAT 机器（`nat = true`）必须填写，每段可带外网起点 `public_from`：转发监听本机端口，上一跳和订阅用对外地址加外网端口。
- **避开已占用的端口**，包括四类：
  - 本机落地节点的监听端口
  - Patato 已分配的转发端口，包括 `manual` 的
  - patato-node 每次同步时上报的本机正在监听的端口，含 Patato 以外的进程，例如 socat
  - 链路发现读到的现有 DNAT 端口段（由运营者确认后登记在 `machines.reserved_ports`）
- **尽量各跳同号**：优先找一个在所有跳上都空闲的端口，排查时一眼能对上。找不到再各跳分别分配。
- **端口稳定**：端口一旦分配，只在删除入口时释放。订阅里的端口不会因为其他变更而变化。
- **冲突**：分配和校验在变更计划的同一事务里完成，预演结果就是实际占用的端口。执行后如果端口被别的进程抢占，这条转发标记为失败并告警，不会自动换端口。换端口会改变订阅，需要运营者确认。

## 转发实现

只做中转的机器上没有落地节点，patato-node 只管理转发。

### 默认：nftables 内核转发

patato-node 通过 netlink 独占维护 `table inet patato`，不依赖 `nft` 命令。每次按完整转发列表原子替换，只增删自己的表，不读写其他表和 iptables 规则。已建立的连接由 conntrack 维持原来的映射，替换规则不会断开它们。

示意（转发 12：本机 41010 → 下一跳 192.0.2.7:41010）：

```
table inet patato {
  counter f12_up {}
  counter f12_down {}

  chain pre {
    type nat hook prerouting priority dstnat; policy accept;
    meta l4proto { tcp, udp } th dport 41010 ct mark set 12 dnat ip to 192.0.2.7:41010
  }
  chain post {
    type nat hook postrouting priority srcnat; policy accept;
    ct mark 12 masquerade
  }
  chain fwd {
    type filter hook forward priority filter; policy accept;
    ct mark 12 ct direction original counter name f12_up
    ct mark 12 ct direction reply    counter name f12_down
  }
}
```

要点：

- **流量计数放在 forward 链**。nat 链只处理每个连接的首包，在 nat 规则上计数得到的是「连接数 × 首包大小」，不是流量。现网入口机上那条 DNAT 规则的计数就是这样。
- **用 ct mark 区分转发**：每条转发占用一个 mark 值（转发 ID），回程包也能对上。本期直接用转发 ID 作为 mark；机器上其他程序也在用 ct mark 时会冲突（见「待确认」）。
- **只处理 IPv4**：DNAT 规则带 `meta nfproto ipv4`，下一跳是 IPv6 的转发自动走用户态。
- **前置条件**：`net.ipv4.ip_forward=1`、root、内核支持 nf_tables。patato-node 不修改 sysctl：前置条件不满足时，这条转发标记为失败并上报原因，由运营者用 tolato 开启。
- **其他防火墙**：如果别的表在 forward 链默认丢包（例如 Docker 或 ufw 把 FORWARD 设为 DROP），本表的 accept 无法覆盖。阶段 3 的探测能发现，首次开线路仍需运营者核对。
- **IPv4 下一跳**：IPv6 客户端进来后无法 NAT 到 IPv4 下一跳。需要 IPv6 入口时用 `userspace`。

### 退回：sing-box direct 入站

机器上没有 nftables、内核不支持、需要 IPv6 到 IPv4 转发，或者运营者指定时，patato-node 在内置 sing-box 里为每条转发建 `direct` 入站，用 `override_address` / `override_port` 指定目标，TCP 和 UDP 都转。

- **入站名称用 `r<转发 ID>`**，和落地节点的 `n<节点 ID>` 分开。流量统计的包装层只认 `n` 开头的入站；混用时，中转连接会被当成未知用户直接断开。
- **计数**：用 sing 的计数回调，不套用户连接的包装层，以保留 Linux 上 TCP 的 `splice` 路径（数据不经用户态内存）。这一点要用基准测试确认。UDP 每个包都要过一次用户态，开销比内核转发大，但比 socat 小得多。

转发模式按机器配置：`auto`（默认，能用 nft 就用）、`nft`、`userspace`。实际生效的模式会上报，并在 Admin 里显示。`auto` 只在「没有 nftables」（不是 Linux、内核不支持、不是 root）时退回用户态；前置条件不满足（`ip_forward` 没开）时不偷偷退回，转发标记为失败并告警，运营者开启后 patato-node 每 10 秒复查一次并自动恢复。

用户态转发用一个独立的内置 sing-box 实例（不是承载节点的那个）：节点内核的「拒绝访问内网」规则不会拦住下一跳，计量层也看不到 `r<id>` 连接。

### 下一跳地址

- **中间跳**：用下一台中转机器的对外地址（`public_address`，未填时用 tolato 上报的 IP）和外网端口。
- **最后一跳**：用落地机器的对外地址（同上；落地机器没有登记时用节点地址）和节点的对外端口 `port`。
- **动态 IP**：落地或中转的 IP 以 tolato 上报为准，变化时 Patato 重新生成上一跳的转发并推送，不再需要 DNS 刷新脚本。IP 变化到重新下发之间，有一个 tolato 上报周期的中断。
- **域名**：下一跳只给了域名时（外部落地），由服务端解析成 IP 后下发，定期重新解析，结果变了就重新下发。当前解析到的 IP 在 Admin 里可见。
- 同一机房的两跳之间走内网：本期没有单独的「供上一跳连接的地址」，需要时把下一台机器的对外地址填成内网地址（会同时影响以它为第一跳的订阅地址）。

## 下发协议

原生节点协议（[`nodeapi`](../nodeapi/nodeapi.go)）新增以下内容，沿用现有的版本号、增量、推送和轮询机制：

- `SyncResponse.Forwards`：本机应有的完整转发列表与版本。每条包含 `id`、`listen_port`、`target_host`（IP）、`target_port`、`mode`。
- `SyncRequest.ForwardsRev`：节点已应用的转发列表版本，没变时面板不重发；空列表也有版本，patato-node 重启后据此清掉不再需要的规则。
- `Settings` 增加 `forward_mode` 和 `probe_interval`。
- `ReportRequest.Forwards`（`ForwardReport{id, up, down, applied, mode, error, at, probe}`）：进入现有 spool，序号去重和重试沿用。计数器按差值上报；读数变小（重启、表重建）视为归零，从新读数开始累计。nft 每次整表重建，替换前先读一次计数，替换后从 0 开始，不丢也不重复。`probe` 是本周期内的 TCP 探测汇总（成功、失败次数，平均耗时，截至周期末的连续失败次数）。
- `ReportRequest.Relay`：实际转发模式与前置条件错误（例如 ip_forward 没开）；`ReportRequest.Listening`：本机正在监听的端口（`/proc/net/{tcp,udp}{,6}`），供分配端口时避开。

没有落地节点的机器也能接入 patato-node，只要在 Patato 里有中转用途即可。

## 状态与告警

- **转发状态**：`pending`（未下发）→ `active`（已应用）/ `failed`（端口被占、前置条件不满足），由 patato-node 上报。`manual` 转发没有状态，只看所在机器是否在线。
- **入口可用**：节点在线，且每一跳机器在线、转发已生效；阶段 3 再加上探测：连续三次 TCP 探测失败视为不可用。
- **订阅**：只下发可用的入口。节点所有入口都不可用时，沿用现有的退回规则：下发离线的入口，避免订阅被清空。
- **告警按机器聚合**：例如「中转 B 掉线，影响 8 条线路、N 名用户」，不会一条入口发一条。事件名见计划（`route_hop_offline`、`route_probe_failed`、`forward_apply_failed`、`route_idle`）。

## 流量统计

- **统计单位是线路**：转发、入口、线路、中转机器四级汇总。小时表保留 30 天，天表长期保留。
- **中转机器总流量**：所有转发之和，可以和云厂商的流量额度对照。
- **长时间没有流量**：线路连续 N 小时为零，但落地节点有流量，提示「这条线路可能没人用或计数异常」。
- **按用户**：中转上做不到。要看某个人走了哪条线路，用落地节点的「用户 × 节点」流量。
- **计数口径**：线路按线上字节统计，落地按用户收发的数据统计，两者天然差几个百分点。报表里分开展示，不互相校正。
- 落地节点按网站和 IP 的访问统计见计划的阶段 4。

## 风险等级

| 操作 | 等级 | 说明 |
| --- | --- | --- |
| 设置中转机器（入口地址、端口段、模式） | 常规 | 修改已在使用的入口地址会改变订阅，此时升为敏感 |
| 建线路、改线路名称 | 常规 | |
| 给节点加入口、按套餐应用线路 | 常规 | 按受影响用户数升级，规则同挂套餐 |
| 修改有入口的线路的跳（增删中转） | 敏感 | 就地改这条线路上所有入口的转发；第一跳变化时订阅地址可能改变。没有入口时为常规 |
| 删除入口或线路、停用入口 | 敏感 | 用户会少一条或几条线路 |
| 修改已分配的端口 | 敏感 | 订阅改变，客户端要刷新订阅 |

## 界面

- **节点详情**：「入口」区块，列出每个入口的链路、状态和今日流量，可以启停、排序、删除。
- **线路页**：每条线路显示经过的中转、挂了几个节点、今天和本月流量、近 7 天曲线、每跳状态；线路详情列出所有入口和各跳转发。
- **机器页**：中转机器显示实际转发模式、转发数、端口段用量、总流量，以及失败的转发。

## 迁移现有链路

导入与登记（第 1、2 步）已实现：`import-xboard` 把子节点导入成父节点的自定义入口；链路发现由 Agent 在每台机器上经 `tolato exec` 执行 `patato route discover` 给出的只读采集命令（Patato 不远程执行），把输出交回 `POST /api/v1/routes:discover` 解析，结果确认后用 `patato node entry adopt` 登记为手写转发，订阅内容不变。第 6 步删除手写规则是运营者操作，Patato 不提供自动删除。

1. **导入**：Xboard 的每个子节点变成父节点的中转入口；父节点在 Xboard 里隐藏的，直连入口默认停用。中间跳 Xboard 里没有记录，导入后由链路发现补齐。补齐前，入口只有第一跳的地址。
2. **链路发现**：从入口的第一跳出发，通过 tolato 只读读取每台机器的 nftables、iptables 和 socat 进程，逐跳追到落地节点。结果交给运营者确认后，登记为 `manual` 转发。只读，不改动任何机器。这一步之后，订阅内容与现网一致，并且已经能按跳监控在线状态。
3. **接入中转机器**：在各中转上安装 patato-node（经 tolato-agent），端口段要避开现有转发。默认的 `40000-49999` 与现网的 60000-62000、63000-63005 不重叠。
4. **并行建托管入口**：同一线路建一个新入口，使用新端口，新旧入口同时下发。按入口逐条验证：转发已生效、测试账号能连通、出口是对应的落地。
5. **切换**：停用 `manual` 入口，订阅随之更新。客户端刷新订阅前，旧链路照常可用。
6. **清理**：观察几天，确认旧端口已经没有流量，再由运营者用 tolato 手动停掉旧的 socat、iptables 规则和 DNS 刷新脚本。Patato 不自动删除它没有创建的规则。

## 已知限制与待确认

- **设备数限制和在线 IP 经过中转后会失真**：落地只能看到最后一跳中转的 IP，所有走中转的用户看起来像同一个 IP，设备数限制对他们实际不起作用。现网用 Xboard 时也是这样。sing-box 1.13 已经去掉了监听端的 PROXY protocol，nftables 也无法插入这个头。可能的方向：中转上报 conntrack 里「客户端 IP ↔ 下一跳源端口」的映射，落地上报连接的源端口，Patato 再把两边对上。工作量和精度都待评估。
- **单点**：一台中转挂了，经过它的所有线路一起中断。可以给同一节点挂两条线路作为备份，由客户端自己选，或用 url-test 分组。第一跳可以用入口组（见上文）配合 DNS 切换。服务端不自动改 DNS。
- **云厂商安全组**：新端口需要在安全组放行，Patato 管不到。
- **待确认**（与计划的「待定」合并跟踪）：
  - 默认端口段：按计划定为 `40000-49999`；
  - 订阅里入口名称的格式：实现为「节点名 · 后缀」，后缀默认线路名；Xboard 导入的入口保留子节点原名；
  - 只有中转入口的节点，所有入口都不可用时是否还退回下发：实现为「套餐里一个可用入口都没有时，下发全部不可用入口」，与现有离线节点回退一致；
  - ct mark 的取值范围是否要避让机器上的其他程序：暂用转发 ID，未避让。

## 实现说明

- 代码：服务端 `server/internal/relay`（端口分配、入口可用性、下一跳、链路发现、周期任务）、`server/internal/ops/relays.go`（变更计划）、`server/internal/ops/relay_group.go`（入口组）、`server/internal/native/relay.go`（下发与上报）；节点端 `node/internal/relay`（nft、用户态、计数、探测）。
- 修改线路的跳（`patato route update <线路> --via a,b,c`，给完整的新跳列表）：线路上已有入口时就地修改每个入口的转发（`server/internal/ops/relay_rehop.go`），不重建入口。
  - 保留的跳沿用原来的转发：ID、端口、流量计数和 patato-node 上的规则都不变，只在下一跳变化时改目标，已建立的连接不受影响。
  - 新增的跳在机器的端口段里分配端口：新的第一跳优先用订阅里的端口（入口覆盖的端口，或原第一跳的外网端口），中间跳优先与后一跳、前一跳同号，都不行时取段内最小的空闲端口。
  - 删掉的跳撤掉它的转发，上一跳改为直接转到它的下一跳。
  - 第一跳换了机器时，入口上覆盖的地址和端口清空，订阅改用新第一跳的对外地址和端口；预演列出每个入口的订阅地址是否改变。
  - 限制：保留的机器不能调换顺序（`route_hops_reordered`，要调换就新建线路）；新加的机器必须已接入 patato-node（`machine_not_enrolled`）；第二跳起的机器要有对外地址或 tolato 上报的 IP（`machine_no_address`）；带手写转发的入口不能就地改跳（`entry_has_manual_forwards`）。
  - 典型用法：入口机原来用整段 DNAT 把端口转到第一跳、入口覆盖了订阅地址时，把入口机加到线路最前面，端口与订阅保持不变，转发生效后再删掉入口机上的手写规则。
- 删除线路、停用入口、删除入口固定为敏感；启用入口常规；设置机器网络属性常规，修改已在使用的第一跳机器的对外地址或端口映射时升为敏感。
- 每跳在线：接入 patato-node 的机器看最近同步或上报（超过 `node.offline_after` 为离线），没接入的看 tolato 的在线状态，都不知道时为「未知」，不撤入口。周期 30 秒，按机器聚合发 `route_hop_offline`（列出受影响入口数和用户数），恢复时发 `route_hop_online`。
- `route_idle`：启用的托管入口第一跳连续 6 小时没有流量、落地节点同期有流量时提示。
- 未验证：真机关口（两跳 TCP/UDP、5% 偏差、重启不重复计数、停机三分钟内撤下）、Linux 网络命名空间测试（`node/internal/relay/nft_netns_test.go`，构建标签 `netns`，需要 root）、用户态 `splice` 路径的基准测试。

## 前置修复

以下两点不论是否做中转都存在，计划的阶段 1 里先修：

- 修改节点时，监听端口（`server_port`）和对外端口（`port`）会被一起覆盖（[nodes.go](../server/internal/ops/nodes.go)）。对外地址与监听地址不同时，一改就会把实际监听端口改坏。应改为两个字段分别修改。
- TLS 节点的默认 SNI 取的是 `address`（[spec.go](../server/internal/native/spec.go)），应该取节点的证书域名。否则入口地址一改，证书就对不上。
