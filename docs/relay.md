# 中转线路设计

> 2026-11-20 · 状态：设计中，尚未开发。排期、阶段关口和落地访问统计见 [中转线路与落地访问监控计划](monitoring.md)，本文是其中「线路、入口与托管转发」的详细设计。两份文档冲突时以计划为准，并同步修改本文。

## 背景

一个落地节点在国内直连往往很慢或连不上，所以客户端先连国内或香港的中转机器，由中转原样转发到落地节点。转发可能不止一跳。现网链路和手写转发的问题见计划的「现状」一节。归纳起来：

- 新增一个落地，要逐台登录中转机器挑端口、写规则；删掉落地后，规则会一直留着。
- 某一跳挂了，面板只看到一批节点同时不通，看不出是哪台中转。
- 落地换了 IP，要逐跳改规则，或者靠额外的 DNS 刷新脚本。
- socat 每个连接 fork 一个进程，小内存中转机器上常驻几百个进程。
- 看不到每条线路走了多少流量。整段 DNAT 规则的计数只是首包，也分不出线路。

## 目标

1. **转发规则零维护**：运营者只说「这些节点走 广州 → 香港」，Patato 自动分配端口、下发规则；节点删除、换机器、换 IP 时，规则自动更新或清理。
2. **订阅里每个入口一条**，例如「洛杉矶 SS · 广州中转」，地址是第一跳。
3. **链路可观测**：每条线路的在线状态和上下行流量；任一跳故障时能说出是哪台机器、影响几条线路。
4. **默认内核转发**，没有条件时才退回用户态。

不做：

- 中转上按用户统计流量。中转只看到加密字节，按用户计费照旧由落地负责。
- 接管 Patato 以外的转发规则。机器上已有的 iptables 和 socat 不改不删。
- 负载均衡、多入口自动择优、按线路计费。

## 概念

数据模型（`routes`、`node_entries`、`forwards` 等表）见计划的「概念与数据模型」。

| 概念 | 含义 |
| --- | --- |
| 落地节点 | 现有的 Patato 节点：跑代理协议、认用户、计流量，不变 |
| 中转机器 | 已接入 patato-node、承担转发的 `machines`。一台机器可以既做落地又做中转 |
| 线路（route） | 有序的中转机器列表，例如「广州 → 香港」=［中转 A，中转 B］，可复用 |
| 入口（entry） | 节点的一个对外地址，订阅里的一条。直连入口没有线路，中转入口绑定一条线路 |
| 转发（forward） | 入口在某一跳上的一条规则：`本机端口 → 下一跳地址:端口`，TCP 和 UDP 都转 |

一个入口经过几跳，就生成几条转发。最后一跳的下一跳是落地节点的监听端口（`server_port`）：

```
入口 = 节点 N（落地 L，监听 33455）经线路［A, B］
  转发 1：A:41010 → B:41010
  转发 2：B:41010 → L:33455
  订阅：A 的入口地址:41010
```

转发有三种 `mode`：

| mode | 谁执行 | 用途 |
| --- | --- | --- |
| `nft` | patato-node，内核转发 | 默认 |
| `userspace` | patato-node 内置的 sing-box | 没有 nftables、需要 IPv6 入口或运营者指定时 |
| `manual` | 运营者手写的规则 | 只登记端口和下一跳，Patato 不下发、不计流量。用于从 Xboard 导入的现有链路 |

此外，一个入口也可以不带线路、只填地址和端口，例如购买的 IPLC。这类入口的状态只跟随落地节点。

## 运营者怎么用

所有操作都先预演，再执行或转审批。命令名以计划的「契约与代码改动范围」为准。

```bash
# 一次性：设置中转机器给客户端的入口地址和可分配端口段
patato machine set <中转 A> --entry-host <给客户端的域名> --relay-ports 40000-49999

# 建线路
patato route create gz-hk --name 广州中转 --via <中转 A>,<中转 B>

# 让节点走这条线路：按套餐或节点选，一次挂一批
patato route apply gz-hk --plan <套餐> --dry-run
patato route apply gz-hk --plan <套餐>

# 单个节点的入口
patato node entry add <节点> --route gz-hk
patato node entry disable <节点> <入口>

# 查看
patato route list
patato route traffic --since 7d
```

Agent 收到「SS 节点都走广州到香港」时，就会执行上面这几条命令。预演结果列出每一跳要占用的端口、新增的订阅条目，以及受影响的用户数。

## 端口分配

- **端口段**：每台中转机器有一个可分配端口段，默认 `40000-49999`，可以按机器覆盖，例如改成云厂商安全组已放行的范围。只在段内分配。
- **避开已占用的端口**，包括四类：
  - 本机落地节点的监听端口
  - Patato 已分配的转发端口，包括 `manual` 的
  - patato-node 每次同步时上报的本机正在监听的端口，含 Patato 以外的进程，例如 socat
  - 链路发现读到的现有 DNAT 端口段
- **尽量各跳同号**：优先找一个在所有跳上都空闲的端口，排查时一眼能对上。找不到再各跳分别分配。
- **端口稳定**：端口一旦分配，只在删除入口时释放。订阅里的端口不会因为其他变更而变化。
- **冲突**：分配和校验在变更计划的同一事务里完成，预演结果就是实际占用的端口。执行后如果端口被别的进程抢占，这条转发标记为失败并告警，不会自动换端口。换端口会改变订阅，需要运营者确认。

## 转发实现

只做中转的机器上没有落地节点，patato-node 只管理转发。

### 默认：nftables 内核转发

patato-node 通过 netlink 独占维护 `table inet patato`，不依赖 `nft` 命令。每次按完整转发列表原子替换，只增删自己的表，不读写其他表和 iptables 规则。已建立的连接由 conntrack 维持原来的映射，替换规则不会断开它们。

示意（转发 12：本机 41010 → 下一跳 192.0.2.7:41010）：

```
table inet patato {
  counter f12_up {}
  counter f12_down {}

  chain pre {
    type nat hook prerouting priority dstnat; policy accept;
    meta l4proto { tcp, udp } th dport 41010 ct mark set 12 dnat ip to 192.0.2.7:41010
  }
  chain post {
    type nat hook postrouting priority srcnat; policy accept;
    ct mark 12 masquerade
  }
  chain fwd {
    type filter hook forward priority filter; policy accept;
    ct mark 12 ct direction original counter name f12_up
    ct mark 12 ct direction reply    counter name f12_down
  }
}
```

要点：

- **流量计数放在 forward 链**。nat 链只处理每个连接的首包，在 nat 规则上计数得到的是「连接数 × 首包大小」，不是流量。现网入口机上那条 DNAT 规则的计数就是这样。
- **用 ct mark 区分转发**：每条转发占用一个 mark 值（转发 ID），回程包也能对上。如果机器上其他程序也在用 ct mark，需要约定 mark 的取值范围，实现时确认。
- **前置条件**：`net.ipv4.ip_forward=1`、root、内核支持 nf_tables。patato-node 不修改 sysctl：前置条件不满足时，这条转发标记为失败并上报原因，由运营者用 tolato 开启。
- **其他防火墙**：如果别的表在 forward 链默认丢包（例如 Docker 或 ufw 把 FORWARD 设为 DROP），本表的 accept 无法覆盖。阶段 3 的探测能发现，首次开线路仍需运营者核对。
- **IPv4 下一跳**：IPv6 客户端进来后无法 NAT 到 IPv4 下一跳。需要 IPv6 入口时用 `userspace`。

### 退回：sing-box direct 入站

机器上没有 nftables、内核不支持、需要 IPv6 到 IPv4 转发，或者运营者指定时，patato-node 在内置 sing-box 里为每条转发建 `direct` 入站，用 `override_address` / `override_port` 指定目标，TCP 和 UDP 都转。

- **入站名称用 `r<转发 ID>`**，和落地节点的 `n<节点 ID>` 分开。流量统计的包装层只认 `n` 开头的入站；混用时，中转连接会被当成未知用户直接断开。
- **计数**：用 sing 的计数回调，不套用户连接的包装层，以保留 Linux 上 TCP 的 `splice` 路径（数据不经用户态内存）。这一点要用基准测试确认。UDP 每个包都要过一次用户态，开销比内核转发大，但比 socat 小得多。

转发模式按机器配置：`auto`（默认，能用 nft 就用）、`nft`、`userspace`。实际生效的模式会上报，并在 Admin 里显示。

### 下一跳地址

- **中间跳**：用下一台中转机器在 tolato 中的 IP。
- **最后一跳**：用落地机器的 IP 和节点的 `server_port`。
- **动态 IP**：落地或中转的 IP 以 tolato 上报为准，变化时 Patato 重新生成上一跳的转发并推送，不再需要 DNS 刷新脚本。IP 变化到重新下发之间，有一个 tolato 上报周期的中断。
- **域名**：下一跳只给了域名时（外部落地），由服务端解析成 IP 后下发，定期重新解析，结果变了就重新下发。当前解析到的 IP 在 Admin 里可见。
- 同一机房的两跳之间可以走内网：机器可配置「供上一跳连接的地址」。

## 下发协议

原生节点协议（[`nodeapi`](../nodeapi/nodeapi.go)）新增以下内容，沿用现有的版本号、增量、推送和轮询机制：

- `SyncResponse.Forwards`：本机应有的完整转发列表与版本。每条包含 `id`、`listen_port`、`target_host`（IP）、`target_port`、`mode`。
- `Settings` 增加转发模式和探测间隔。
- `ForwardReport{id, up, down, applied, mode, error}`：进入现有 spool，序号去重和重试沿用。计数器按差值上报；读数变小（重启、表重建）视为归零，从新读数开始累计。阶段 3 再加上探测结果。
- 本机正在监听的端口列表，供分配端口时避开。

没有落地节点的机器也能接入 patato-node，只要在 Patato 里有中转用途即可。

## 状态与告警

- **转发状态**：`pending`（未下发）→ `active`（已应用）/ `failed`（端口被占、前置条件不满足），由 patato-node 上报。`manual` 转发没有状态，只看所在机器是否在线。
- **入口可用**：节点在线，且每一跳机器在线、转发已生效；阶段 3 再加上探测：连续三次 TCP 探测失败视为不可用。
- **订阅**：只下发可用的入口。节点所有入口都不可用时，沿用现有的退回规则：下发离线的入口，避免订阅被清空。
- **告警按机器聚合**：例如「中转 B 掉线，影响 8 条线路、N 名用户」，不会一条入口发一条。事件名见计划（`route_hop_offline`、`route_probe_failed`、`forward_apply_failed`、`route_idle`）。

## 流量统计

- **统计单位是线路**：转发、入口、线路、中转机器四级汇总。小时表保留 30 天，天表长期保留。
- **中转机器总流量**：所有转发之和，可以和云厂商的流量额度对照。
- **长时间没有流量**：线路连续 N 小时为零，但落地节点有流量，提示「这条线路可能没人用或计数异常」。
- **按用户**：中转上做不到。要看某个人走了哪条线路，用落地节点的「用户 × 节点」流量。
- **计数口径**：线路按线上字节统计，落地按用户收发的数据统计，两者天然差几个百分点。报表里分开展示，不互相校正。
- 落地节点按网站和 IP 的访问统计见计划的阶段 4。

## 风险等级

| 操作 | 等级 | 说明 |
| --- | --- | --- |
| 设置中转机器（入口地址、端口段、模式） | 常规 | 修改已在使用的入口地址会改变订阅，此时升为敏感 |
| 建线路、改线路名称 | 常规 | |
| 给节点加入口、按套餐应用线路 | 常规 | 按受影响用户数升级，规则同挂套餐 |
| 修改线路的跳（增删中转、调整顺序） | 敏感 | 会重建这条线路上所有入口的转发，并可能改变入口地址 |
| 删除入口或线路、停用入口 | 敏感 | 用户会少一条或几条线路 |
| 修改已分配的端口 | 敏感 | 订阅改变，客户端要刷新订阅 |

## 界面

- **节点详情**：「入口」区块，列出每个入口的链路、状态和今日流量，可以启停、排序、删除。
- **线路页**：每条线路显示经过的中转、挂了几个节点、今天和本月流量、近 7 天曲线、每跳状态；线路详情列出所有入口和各跳转发。
- **机器页**：中转机器显示实际转发模式、转发数、端口段用量、总流量，以及失败的转发。

## 迁移现有链路

1. **导入**：Xboard 的每个子节点变成父节点的中转入口；父节点在 Xboard 里隐藏的，直连入口默认停用。中间跳 Xboard 里没有记录，导入后由链路发现补齐。补齐前，入口只有第一跳的地址。
2. **链路发现**：从入口的第一跳出发，通过 tolato 只读读取每台机器的 nftables、iptables 和 socat 进程，逐跳追到落地节点。结果交给运营者确认后，登记为 `manual` 转发。只读，不改动任何机器。这一步之后，订阅内容与现网一致，并且已经能按跳监控在线状态。
3. **接入中转机器**：在各中转上安装 patato-node（经 tolato-agent），端口段要避开现有转发。默认的 `40000-49999` 与现网的 60000-62000、63000-63005 不重叠。
4. **并行建托管入口**：同一线路建一个新入口，使用新端口，新旧入口同时下发。按入口逐条验证：转发已生效、测试账号能连通、出口是对应的落地。
5. **切换**：停用 `manual` 入口，订阅随之更新。客户端刷新订阅前，旧链路照常可用。
6. **清理**：观察几天，确认旧端口已经没有流量，再由运营者用 tolato 手动停掉旧的 socat、iptables 规则和 DNS 刷新脚本。Patato 不自动删除它没有创建的规则。

## 已知限制与待确认

- **设备数限制和在线 IP 经过中转后会失真**：落地只能看到最后一跳中转的 IP，所有走中转的用户看起来像同一个 IP，设备数限制对他们实际不起作用。现网用 Xboard 时也是这样。sing-box 1.13 已经去掉了监听端的 PROXY protocol，nftables 也无法插入这个头。可能的方向：中转上报 conntrack 里「客户端 IP ↔ 下一跳源端口」的映射，落地上报连接的源端口，Patato 再把两边对上。工作量和精度都待评估。
- **单点**：一台中转挂了，经过它的所有线路一起中断。可以给同一节点挂两条线路作为备份，由客户端自己选，或用 url-test 分组。服务端暂不做自动切换。
- **云厂商安全组**：新端口需要在安全组放行，Patato 管不到。
- **待确认**（与计划的「待定」合并跟踪）：
  - 默认端口段；
  - 订阅里入口名称的格式，例如「节点名 · 线路名」；
  - 只有中转入口的节点，所有入口都不可用时是否还退回下发；
  - ct mark 的取值范围是否要避让机器上的其他程序。

## 前置修复

以下两点不论是否做中转都存在，计划的阶段 1 里先修：

- 修改节点时，监听端口（`server_port`）和对外端口（`port`）会被一起覆盖（[nodes.go](../server/internal/ops/nodes.go)）。对外地址与监听地址不同时，一改就会把实际监听端口改坏。应改为两个字段分别修改。
- TLS 节点的默认 SNI 取的是 `address`（[spec.go](../server/internal/native/spec.go)），应该取节点的证书域名。否则入口地址一改，证书就对不上。
